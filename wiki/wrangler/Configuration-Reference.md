# Configuration Reference

Wrangler reads project configuration from a file in your project root. This page documents every configuration option, binding type, and environment pattern.

See also: [[Home]] for global flags, [[Workers-Lifecycle]] for deploy commands, [[Security]] for secrets management.

---

## Config File Formats

Wrangler supports three configuration file formats, checked in this order:

1. **`wrangler.jsonc`** -- JSON with comments (recommended for v4+)
2. **`wrangler.json`** -- Standard JSON
3. **`wrangler.toml`** -- TOML (legacy, still fully supported)

You can override the config file path with the `--config` / `-c` flag:

```bash
wrangler dev --config ./configs/wrangler.staging.jsonc
```

> **Recommendation:** Use `wrangler.jsonc` for new projects. It supports inline comments, is closer to the API's JSON schema, and is the default format generated by `wrangler init` in v4.

## Top-Level Configuration

These are the most commonly used top-level fields.

```jsonc
{
  // Required
  "name": "my-worker",                    // Worker name (used as subdomain on workers.dev)
  "main": "src/index.ts",                 // Entry point file
  "compatibility_date": "2025-04-01",     // Workers runtime compatibility date

  // Optional basics
  "account_id": "abcdef1234567890",       // Cloudflare account ID
  "workers_dev": true,                    // Enable *.workers.dev subdomain (default: true)
  "compatibility_flags": [                // Opt into specific runtime features
    "nodejs_compat",
    "streams_enable_constructors"
  ],

  // Build
  "minify": false,                        // Minify bundled output
  "node_compat": true,                    // Enable Node.js compatibility (deprecated, use nodejs_compat flag)
  "no_bundle": false,                     // Skip bundling (use if you have a custom build step)
  "find_additional_modules": false,       // Resolve modules outside the entrypoint
  "preserve_file_names": false,           // Keep original file names in the bundle

  // Build command (optional custom build step)
  "build": {
    "command": "npm run build",           // Shell command to run before deploying
    "cwd": ".",                           // Working directory for the build command
    "watch_dir": "src"                    // Directory to watch for changes during `wrangler dev`
  },

  // Assets (static file serving alongside the Worker)
  "assets": {
    "directory": "./public",              // Directory of static files
    "binding": "ASSETS",                  // Optional binding name to access assets in code
    "html_handling": "auto-trailing-slash",
    "not_found_handling": "single-page-application"
  },

  // Pages-specific
  "pages_build_output_dir": "./dist",     // Output dir for Pages projects

  // Limits
  "limits": {
    "cpu_ms": 50                          // CPU time limit in milliseconds
  },

  // Placement
  "placement": {
    "mode": "smart"                       // Smart placement (auto-locate near data)
  },

  // Observability
  "observability": {
    "enabled": true,                      // Enable Workers Logs
    "head_sampling_rate": 1               // Sampling rate (0 to 1)
  },

  // Tail consumers (send logs to another Worker)
  "tail_consumers": [
    { "service": "log-collector" }
  ]
}
```

## Routes and Custom Domains

### Routes

Routes attach your Worker to URL patterns on zones you control.

```jsonc
{
  "routes": [
    // Route with zone name (Wrangler resolves the zone ID)
    { "pattern": "api.example.com/v1/*", "zone_name": "example.com" },

    // Route with explicit zone ID
    { "pattern": "api.example.com/v2/*", "zone_id": "abc123def456" },

    // Simple string route (requires account-level routing)
    "api.example.com/health"
  ]
}
```

### Custom Domains

Custom domains are a simpler alternative to routes. Cloudflare automatically provisions DNS and SSL.

```jsonc
{
  "custom_domains": [
    "api.example.com",
    "api.example.org"
  ]
}
```

> **Difference:** Routes require you to manage DNS records separately. Custom domains handle DNS and SSL automatically.

## Cron Triggers

Schedule your Worker to run on a recurring schedule using cron syntax.

```jsonc
{
  "triggers": {
    "crons": [
      "0 * * * *",           // Every hour
      "0 0 * * *",           // Every day at midnight
      "*/5 * * * *",         // Every 5 minutes
      "0 9 * * MON-FRI"      // Weekdays at 9 AM
    ]
  }
}
```

Your Worker handles cron triggers with the `scheduled` event:

```typescript
export default {
  async scheduled(event: ScheduledEvent, env: Env, ctx: ExecutionContext) {
    ctx.waitUntil(doWork(env));
  },
};
```

Test locally with `wrangler dev --test-scheduled`, then visit `http://localhost:8787/__scheduled`.

## Multi-Environment Setup

Environments let you deploy the same Worker code with different configurations (name, routes, bindings, secrets) for staging, production, etc.

### JSONC format

```jsonc
{
  // Top-level: shared defaults
  "name": "my-api",
  "main": "src/index.ts",
  "compatibility_date": "2025-04-01",
  "kv_namespaces": [
    { "binding": "CACHE", "id": "shared-kv-id" }
  ],

  // Environment overrides
  "env": {
    "staging": {
      "name": "my-api-staging",
      "routes": [
        { "pattern": "staging-api.example.com/*", "zone_name": "example.com" }
      ],
      "kv_namespaces": [
        { "binding": "CACHE", "id": "staging-kv-id" }
      ],
      "vars": {
        "ENVIRONMENT": "staging",
        "LOG_LEVEL": "debug"
      }
    },
    "production": {
      "name": "my-api-production",
      "routes": [
        { "pattern": "api.example.com/*", "zone_name": "example.com" }
      ],
      "kv_namespaces": [
        { "binding": "CACHE", "id": "production-kv-id" }
      ],
      "vars": {
        "ENVIRONMENT": "production",
        "LOG_LEVEL": "warn"
      }
    }
  }
}
```

### Using environments

```bash
# Deploy to staging
wrangler deploy --env staging

# Deploy to production
wrangler deploy --env production

# Dev with staging config
wrangler dev --env staging

# Tail production logs
wrangler tail --env production
```

### Inheritance rules

- Environment-specific settings **override** top-level settings.
- Most fields are inherited if not specified in the environment block.
- Bindings (KV, R2, D1, etc.) are **not** merged -- if you specify any binding of a type in an environment, you must specify all bindings of that type.

## Bindings

Bindings connect your Worker to Cloudflare resources. Each binding creates a variable available in your Worker's `env` parameter.

### KV Namespaces

```jsonc
{
  "kv_namespaces": [
    {
      "binding": "MY_KV",                         // Variable name in code
      "id": "abcdef1234567890abcdef1234567890",    // KV namespace ID
      "preview_id": "preview-kv-id-here"           // Optional: separate namespace for `wrangler dev --remote`
    }
  ]
}
```

Usage: `await env.MY_KV.get("key")`

### R2 Buckets

```jsonc
{
  "r2_buckets": [
    {
      "binding": "MY_BUCKET",
      "bucket_name": "my-storage-bucket",
      "preview_bucket_name": "my-storage-bucket-preview",  // Optional
      "jurisdiction": "eu"                                  // Optional: data jurisdiction
    }
  ]
}
```

Usage: `await env.MY_BUCKET.put("file.txt", data)`

### D1 Databases

```jsonc
{
  "d1_databases": [
    {
      "binding": "MY_DB",
      "database_name": "my-database",
      "database_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
      "preview_database_id": "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy",  // Optional
      "migrations_dir": "./migrations",                                // Optional
      "migrations_table": "d1_migrations"                              // Optional
    }
  ]
}
```

Usage: `await env.MY_DB.prepare("SELECT * FROM users WHERE id = ?").bind(id).first()`

### Durable Objects

```jsonc
{
  "durable_objects": {
    "bindings": [
      {
        "name": "COUNTER",                        // Variable name in code
        "class_name": "CounterObject",            // Durable Object class name
        "script_name": "counter-worker",          // Optional: if the DO is in another Worker
        "environment": "production"               // Optional: environment of the other Worker
      }
    ]
  },

  // If the Durable Object class is defined in THIS Worker, declare the migration
  "migrations": [
    {
      "tag": "v1",
      "new_classes": ["CounterObject"]
    }
  ]
}
```

Usage: `const id = env.COUNTER.idFromName("my-counter"); const stub = env.COUNTER.get(id);`

### Queues

```jsonc
{
  "queues": {
    "producers": [
      {
        "binding": "MY_QUEUE",
        "queue": "my-queue-name"
      }
    ],
    "consumers": [
      {
        "queue": "my-queue-name",
        "max_batch_size": 10,
        "max_batch_timeout": 5,
        "max_retries": 3,
        "dead_letter_queue": "my-dlq",
        "max_concurrency": 1,
        "retry_delay": 60
      }
    ]
  }
}
```

Producer: `await env.MY_QUEUE.send({ type: "order", id: 123 })`

Consumer handler:

```typescript
export default {
  async queue(batch: MessageBatch<any>, env: Env) {
    for (const msg of batch.messages) {
      console.log(msg.body);
      msg.ack();
    }
  },
};
```

### Service Bindings (Worker-to-Worker)

```jsonc
{
  "services": [
    {
      "binding": "AUTH_SERVICE",
      "service": "auth-worker",
      "environment": "production",      // Optional
      "entrypoint": "AuthHandler"       // Optional: named entrypoint
    }
  ]
}
```

Usage: `const resp = await env.AUTH_SERVICE.fetch(request)`

### Analytics Engine

```jsonc
{
  "analytics_engine_datasets": [
    {
      "binding": "ANALYTICS",
      "dataset": "my-dataset"           // Optional: defaults to the binding name
    }
  ]
}
```

Usage: `env.ANALYTICS.writeDataPoint({ blobs: ["click"], doubles: [1], indexes: ["page-home"] })`

### Vectorize

```jsonc
{
  "vectorize": [
    {
      "binding": "MY_INDEX",
      "index_name": "product-embeddings"
    }
  ]
}
```

Usage: `await env.MY_INDEX.query(vector, { topK: 10 })`

### Hyperdrive

```jsonc
{
  "hyperdrive": [
    {
      "binding": "MY_PG",
      "id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
    }
  ]
}
```

Usage: `const connectionString = env.MY_PG.connectionString; // Use with your Postgres client`

### AI

```jsonc
{
  "ai": {
    "binding": "AI"
  }
}
```

Usage: `const result = await env.AI.run("@cf/meta/llama-3.1-8b-instruct", { prompt: "Hello" })`

### Browser Rendering

```jsonc
{
  "browser": {
    "binding": "BROWSER"
  }
}
```

Usage: `const browser = await puppeteer.launch(env.BROWSER)`

### mTLS Certificates

```jsonc
{
  "mtls_certificates": [
    {
      "binding": "MY_CERT",
      "certificate_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
    }
  ]
}
```

Usage: `const resp = await fetch("https://mutual-tls-api.example.com", { client: env.MY_CERT })`

See [[Security]] for how to upload mTLS certificates.

### Email (Send Workers)

```jsonc
{
  "send_email": [
    {
      "name": "EMAIL",
      "destination_address": "alerts@example.com"  // Optional: restrict destination
    }
  ]
}
```

## Plain-Text Variables

Non-secret environment variables are defined with `vars`:

```jsonc
{
  "vars": {
    "ENVIRONMENT": "production",
    "API_BASE_URL": "https://api.example.com",
    "LOG_LEVEL": "info",
    "MAX_RETRIES": "3"
  }
}
```

Usage: `env.ENVIRONMENT`, `env.API_BASE_URL`

> All values are strings. For secrets (encrypted values that are not visible in config), use `wrangler secret put` instead. See [[Security]].

## Experimental Provisioning

The `--experimental-provision` flag lets Wrangler automatically create the bound resources (KV namespaces, R2 buckets, D1 databases) that are declared in your config but do not yet exist.

```bash
wrangler deploy --experimental-provision
```

This is useful for bootstrapping new environments or onboarding new developers without requiring them to manually create each resource first.

```bash
# First deploy: auto-create all bindings that don't exist yet
wrangler deploy --env staging --experimental-provision
```

> **Note:** This is an experimental feature and its behavior may change. It creates resources with default settings. For production, you should create resources explicitly with their respective commands (e.g., `wrangler kv namespace create`).

## Legacy TOML Format

For reference, the same core configuration in TOML looks like:

```toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "2025-04-01"
compatibility_flags = ["nodejs_compat"]

[vars]
ENVIRONMENT = "production"

[[kv_namespaces]]
binding = "MY_KV"
id = "kv-namespace-id"

[[r2_buckets]]
binding = "MY_BUCKET"
bucket_name = "my-bucket"

[env.staging]
name = "my-worker-staging"

[env.staging.vars]
ENVIRONMENT = "staging"

[[env.staging.kv_namespaces]]
binding = "MY_KV"
id = "kv-staging-id"
```

TOML is fully supported but is considered legacy. The JSONC format is recommended for new projects because it aligns with the API schema, supports comments, and is the default in Wrangler v4.

## Tips

- **Always set `compatibility_date`** to a recent date when starting a project, then update it deliberately when ready to adopt new behavior.
- **Use `nodejs_compat`** in `compatibility_flags` if you need Node.js built-in modules (e.g., `crypto`, `buffer`, `stream`).
- **`preview_id`** fields on bindings let you use separate resources during `wrangler dev --remote`, preventing local development from touching production data.
- **Run `wrangler types`** after editing bindings to regenerate TypeScript types.
- **Bindings are not merged across environments.** If your staging environment needs KV, you must declare all KV bindings in the staging block, even if some are the same as the top-level ones.
- **Smart placement** (`"placement": { "mode": "smart" }`) lets Cloudflare automatically run your Worker closer to your data sources (e.g., your database region).
- **`--experimental-provision`** is helpful for bootstrapping but should not replace explicit resource creation in production workflows.
