// Phased Implementation
PHASE 01

Experiment Logger Instrumentation

Modify autoresearch loop to persist structured experiment records with score, context, and client_id. This is the foundation — everything else depends on clean experiment output.

Add ExperimentRecord schema: client_id, run_id, problem, solution, score, timestamp, account_snapshot
Write to SQLite experiments table (extend claude-mem or new DB)
Score normalization: ensure 0.0–1.0 float, not pass/fail binary
Tag each record with data sources used (GTM / Google Ads / Meta)
sqlite autoresearch
PHASE 02

Account State Collector

Pull and normalize client account data from GTM, Google Ads MCP, and Pipeboard Meta MCP into a structured AccountState object stored per client. This becomes the system prompt context.

GTM: export container JSON → parse tags/triggers/variables into schema
Google Ads MCP: pull campaigns, conversion actions, account structure
Pipeboard Meta MCP: pull pixel events, CAPI config, ad account structure
Serialize to clients/{client_id}/account_state.json, versioned
Snapshot on each autoresearch run (state at time of experiment)
GTM MCP Google Ads Meta MCP
PHASE 03

Training Data Pipeline

Filter high-scoring experiments, inject account state into system prompts, and export clean JSONL training files per client. This is the core transformation step.

Score filter: score ≥ 0.75 (configurable threshold per client)
Deduplication: cosine similarity on solution text via Chroma
System prompt builder: inject client AccountState + role context
Export: training/{client_id}/v{N}.jsonl in OpenAI fine-tune format
Minimum 50 examples gate before fine-tune is triggered
chroma jsonl
PHASE 04

Fine-Tune Runner

Two-track runner: OpenAI API for fast cloud fine-tunes, Ollama/MLX for private local fine-tunes on M3 Ultra. Triggered automatically when new JSONL version is ready.

Track A — OpenAI: upload JSONL → create fine-tune job → poll status → register model ID
Track B — Ollama: convert JSONL → Modelfile → ollama create client-{id}-v{N} on M3 Ultra
Model registry: models/{client_id}.json tracking versions, eval scores, active flag
Eval harness: 10-question holdout set per client, auto-score new model before promoting
OpenAI API Ollama M3 Ultra
PHASE 05

OpenClaw Client Brain Integration

Route requests through OpenClaw gateway to the correct client-specialized model. Each client_id maps to an active model version. No context dump required at inference.

OpenClaw middleware: read x-client-id header → lookup active model in registry
Route to local Ollama client model OR OpenAI fine-tuned model per flag
Fallback: if no client model ready, use full AccountState as RAG context
Telemetry: log which model version handled each request for drift tracking
OpenClaw :18789
PHASE 06

Flywheel Automation

Close the loop. New autoresearch runs automatically trigger re-scoring, JSONL delta append, and retrain when enough new high-quality examples accumulate. Model gets smarter with every client engagement.

Watcher: after each autoresearch run, check if new high-score count ≥ threshold (default 20)
Auto-append to JSONL, bump version, trigger fine-tune runner
Drift detection: compare eval scores v(N) vs v(N-1), rollback if regression
Slack/notification: post model promotion events to client channel
cron flywheel

⟳ The Compounding Moat

Every client engagement generates experiments. Every experiment above threshold extends the training set. Every retrain makes the model more accurate for that client's specific patterns. At ~500 high-quality examples per client, the model knows their full tracking architecture better than any human consultant who hasn't lived in their accounts for years. This is the retention mechanic — the model is an asset that only you and the client share.
