A GTM loop that learns from its own reverts.

GTM Autoresearch already scores a client's container on 12 dimensions, mutates it, and keeps or reverts each change overnight. This box adds the second loop from the Karpathy-loop playbook: it reads every run's ledger, names the habits that keep failing, and proposes a rewrite of how the loop works. The scorer and the rules stay locked, and the owner still publishes.

The stuck target was a scorer rule the loop couldn't satisfy.

After round 5 the only error left in BLADE's container was CE - GA4 Ecom Events: a regex trigger matching view_item_list|select_item|view_cart|add_payment_info, flagged for lacking an EQUALS filter. pickStrategy() always picks the lowest-scoring dimension with an error, and the scores never changed, so it picked trigger quality 24 times. A real fix splits the trigger into 4 EQUALS triggers and re-points 2 tags: 6 entity changes against a budget of 3. Every attempt broke something and was reverted. Both clients show the same pattern, which makes it a habit, not an accident.

To raise the consent dimension, the loop set consentStatus: NEEDED and stopped there. The scorer counts that as 100%. The guide's audit counts a NEEDED tag with no consent types as high severity. BLADE went from 105 medium findings (no consent setting) to 114 high ones; HRE from 0 to 20, and HRE's winner also added 2 Custom HTML or Custom JavaScript entities, which the guide treats as a hard stop. AutoLoop turns this into a how-to-work rule below. The scorer fix goes to the owner, because AutoLoop may not touch evals/.

Exhibit E · AutoLoop's first read

Seven habits across two clients, and the rewrite it proposes

AutoLoop may change one section of each program.md: "Edit Strategy", the how-to-work part. Constraints, the mutation budget, stop conditions, the weights and evals/ are fixed rules a human owns. The autoloop-scope check applies each proposal to a copy and confirms every other section is byte-identical. Nothing has been written to program.md.

The rewrite won't do anything yet.

parseProgram() in run-gtm-loop.ts reads only the template and snapshot paths. The strategy order and constraints are hardcoded arrays, and pickStrategy() ignores the strategy order anyway. Until the loop reads "Edit Strategy" from program.md, an AutoLoop rewrite, or a human one, changes nothing. That is the first fix in the plan. The second is recording what each reverted round tried, because AutoLoop can only see 2 of its 3 habits without it.

Exhibit G · Phased plan

Build order, gate by gate

Phase 0this session

Box exists and runs. arb CLI with 27 checks, the Jev guide's reader and audit vendored in box/jev/, AutoLoop analyzer, Worker with SSE stream, D1 schema, box.yml CI, and a recorded proof run on the real repo. Branch feat/autoresearch-in-a-box.

Phase 1 · G1lock the scorer

Make the contract real. Add .claude/settings.json denying edits to evals/**. Rewrite parseProgram() to read Constraints, Mutation Budget and Edit Strategy from program.md, and make pickStrategy() follow them. Fix HRE's weights table or add Google Ads to its snapshot so 12 means 12.

Phase 2 · G2a ledger that teaches

Record every attempt. Each round writes strategy, operations, candidate dimensions and the dimensions still failing, reverted or not. Add a stall stop (3 reverts in a row on an unchanged container). Keep manifest.json pointed at the best winner automatically.

Phase 3 · G3AutoLoop live

Proposals as pull requests. arb autoloop --pr opens a PR touching only Edit Strategy, with the evidence rounds in the body. Only the owner merges. Rerun BLADE with the merged habits and compare against 77.3%.

Phase 4 · G4the Jev lane

Passing the scorer isn't done. Put the guide's hard stops in shadowPolicy(), fix the shared reader so built-in triggers resolve, run the guide's audit on every candidate and reject any keep that adds high or critical findings. Wire the guide's question set through a multi-question jev-gateway route. Then preview-mode QA per kept round and jev-site-scan for configured vs observed. Jev stays shadow-only.

Phase 5deploy + distribute

One link per client. Deploy the Worker, point CI at it, and publish the guide under guide.organizedai.vip/gtm-autoresearch/box. Package box/ so a new client folder gets the same gates.

G1  Copy box/templates/claude-settings.json to .claude/settings.json (deny Edit/Write on evals/** and box/checks/**). G3  Add `arb autoloop --pr`: writes the proposal to a branch and opens a PR that changes only the Edit Strategy section, with the evidence rounds in the body. Only the owner merges. Then rerun BLADE with the merged habits and report the score against 77.3%.
G4  The Jev lane (guide.organizedai.vip/jev-container-json). Add the guide's hard stops to shadowPolicy() in scripts/jev-shadow.ts ahead of the judge: consent touched, opaque code touched, unresolved refs, partial export. Run the guide's audit on every candidate and revert any keep that adds high or critical findings (today BLADE goes 43→157 high). Then per kept round, run a Playwright check in GTM preview mode and pass it as qa, and call jev-site-scan to compare configured vs observed tags. Jev stays shadow-only.
